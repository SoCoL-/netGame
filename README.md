# supreme_game

A [libGDX](https://libgdx.com/) project generated with [gdx-liftoff](https://github.com/libgdx/gdx-liftoff),
into which сетевая RTS-логика (создание/движение/бой юнитов, дом игрока,
условие победы) была интегрирована из отдельного прототипа.

## Модули

- `shared` — ECS-компоненты и системы (Ashley), общие для сервера и
  клиента, плюс сетевой протокол (KryoNet-сообщения). Без зависимости на
  графику — только `gdx-core` (математика), `ashley`, `kryonet`.
- `server` — headless-процесс: авторитетная симуляция, применение правил
  игры (лимит юнитов, урон, условие победы). Не использует ни `core`, ни
  графику — только `shared`. Запуск: `./gradlew :server:run`.
- `core`: основной модуль игровой логики, общей для всех клиентских
  платформ — `Main`, `GameScreen`, рендер, ввод, сетевой клиент
  (`ru.socol.supreme.network.GameClient`).
- `lwjgl3`: десктопная платформа (LWJGL3) — было `desktop` в старых доках.
- `android`: мобильная Android-платформа. Нужен Android SDK.

Сервер — это отдельный, самостоятельный процесс, который не собирается ни
в APK, ни в десктопный джар клиента: его запускают на одной машине (обычно
на PC), а клиенты (`lwjgl3` и/или `android`) подключаются к нему по сети.

## Управление

- **WASD / стрелки** — прокрутка камеры (карта 2000x2000, окно не помещает её целиком)
- **ЛКМ клик по своему юниту** — выбрать только его
- **ЛКМ протяжка (рамка)** — выбрать все свои юниты внутри рамки (здания рамкой не выделяются)
- **ЛКМ клик по своему зданию** — открыть/закрыть панель постройки (повторный клик по нему же или клик куда-то ещё закрывает панель)
- **ЛКМ клик по пустому месту** — снять выделение
- **ПКМ по вражескому юниту/зданию** (при непустом выделении) — атаковать им всем выделением сразу
- **ПКМ по пустому месту / своему юниту** — приказ на движение всем выделенным юнитам (несколько юнитов расходятся сеткой вокруг точки клика)
- **`** (клавиша над Tab, слева от "1") — переключает отладочный режим отрисовки (см. ниже)
- **B** — открывает меню постройки (шахта железа / казарма стрелков / электростанция / хранилище железа / хранилище электричества); после выбора превью следует за курсором (шахта — "прилипает" к месторождению, остальные — свободно), ЛКМ подтверждает (только пока превью зелёное), повторный B отменяет

Весь текст на экране (статус подключения, "VICTORY"/"DEFEAT"/"DRAW", панель
постройки) — на английском, хотя код и README на русском. Причина
техническая: `BitmapFont()` по умолчанию в LibGDX — встроенный битмап-шрифт
только с латиницей, кириллических глифов в нём физически нет, кириллица
рисовалась бы пустыми прямоугольниками. Правильный, но более тяжёлый
вариант — сгенерировать битмап-шрифт из настоящего TTF с кириллицей через
`FreeTypeFontGenerator` (`gdx-freetype` уже есть в зависимостях `core`),
но для этого нужен сам файл шрифта с нужной лицензией, которого в проекте
пока нет. Раз игровой текст минимален, английский — самый простой рабочий
вариант без лишних ассетов.

## Как запустить

**Проще всего — собрать два самодостаточных jar-файла один раз и дальше запускать их напрямую, без Gradle/IDE:**

```bash
./gradlew buildJars
# соберёт build/dist/server.jar, build/dist/client.jar и скопирует units.json

java -jar build/dist/server.jar
java -jar build/dist/client.jar                 # клиент, сервер на localhost
java -jar build/dist/client.jar 192.168.1.50     # клиент с явным адресом сервера
```

Оба jar-файла самодостаточны (все зависимости внутри, включая нативные
библиотеки LWJGL3 у клиента) — их можно скопировать на другую машину и
запустить одной командой `java -jar ...`, ничего больше не нужно.
`units.json` рядом с `server.jar` — не зависимость, а настраиваемые
данные: баланс юнитов можно менять прямо в нём, без пересборки (см.
"Баланс юнитов — данные, а не код" ниже).

Это же решает проблему с кнопкой Run в Android Studio на `main()`: она
использует отдельную синтетическую задачу, которая не подхватывает JVM-флаги
и working directory из `lwjgl3/build.gradle` (в частности
`--enable-native-access=ALL-UNNAMED`, нужный LWJGL3 для создания окна на
новых JDK) — из-за этого окно клиента может не появляться вовсе, при том
что процесс запускается. `java -jar client.jar` (как и `./gradlew :lwjgl3:run`)
этой проблемы не имеет, потому что использует настоящую, полностью
настроенную сборку.

Альтернатива — гонять напрямую через Gradle-таски, без сборки jar-ов
(удобно во время разработки, пересобирает только изменившееся):

```bash
# Сервер (в одном терминале)
./gradlew :server:run

# Десктопный клиент (в другом терминале; для локального теста 2 игроков — ещё в третьем)
./gradlew :lwjgl3:run

# Клиент с явным адресом сервера (по умолчанию — localhost):
./gradlew :lwjgl3:run --args="192.168.1.50"
```

Для Android: соберите/запустите модуль `android` как обычное Android-приложение
(нужен Android SDK и, для эмулятора, `local.properties` с `sdk.dir`). Адрес
сервера сейчас захардкожен в `AndroidLauncher` как `10.0.2.2` — это
специальный алиас Android-эмулятора на loopback хост-машины, где по
умолчанию и предполагается локально запущенный сервер. **На реальном
устройстве это работать не будет** — нужен настоящий IP/хост сервера в
локальной сети или в интернете; для реального использования стоит
добавить экран ввода адреса перед стартом `GameScreen`, вместо константы.

## Слои отрисовки

Два режима, переключаются клавишей `` ` `` (`GameScreen.debugMode`):

- **Обычный** (по умолчанию) — земля залита сплошным цветом:
  `GRASS_COLOR` (зелёный, "трава") на весь `MAP_WIDTH x MAP_HEIGHT`, поверх
  неё `WATER_COLOR` (голубой) точно в границах `GameConstants.WATER_*`.
  Юниты и здания рисуются как раньше, без изменений.
- **Отладочный** — вместо заливки земля разлинована в сетку с шириной
  клетки `PATH_GRID_CELL_SIZE` (та же, с которой работает A*), только
  грани клеток (`ShapeType.Line`), без заливки. Цвет клетки решает
  `Pathfinding.isWaterCell(cx, cy)` — та же классификация (с той же
  `PATH_CLEARANCE`-инфляцией), которую реально видит пасфайндер, а не
  повторение сырой геометрии воды напрямую — это отладочный вид именно
  внутреннего состояния A*, полезный ровно для такого рода багов, какой
  чинили выше. Дополнительно поверх рисуются маршруты всех движущихся
  юнитов оранжевыми линиями — от текущей позиции через
  `direction.target`, дальше через все оставшиеся точки `PathComponent`,
  если юнит обходит препятствие. У юнита без активного движения линии нет.

Маршрут — единственное, что реально гоняется по сети специально ради
отладочного режима: `UnitSnapshot.pathPoints` заполняется сервером всегда
(не только когда у клиента включён debug-режим — специального
клиент-сервер согласования по этому поводу нет, это самый простой вариант
для масштаба проекта, а не потому что дешевле было бы иначе). Здание/цвет
клетки клиент считает сам, без сети — `Pathfinding.isWaterCell` использует
только константы `GameConstants`, одинаковые на клиенте и сервере.

**Из-за pathPoints пришлось увеличить буферы KryoNet.** `Server()`/`Client()`
без аргументов используют дефолтные буферы KryoNet — 16384 байт на запись
и всего 2048 байт на один сериализуемый объект. Пока `WorldSnapshot` был
компактным, этого хватало; с ростом числа юнитов и особенно после
`pathPoints` (по несколько точек на каждого движущегося юнита) снапшот на
несколько десятков юнитов уже не помещался в 2048 байт — сериализация
падала с переполнением буфера (баг воспроизводился на ~40 юнитах, по 20
на игрока). И `GameServer`, и `GameClient` теперь создают
`Server`/`Client` с явными `GameConstants.NETWORK_WRITE_BUFFER_SIZE` /
`NETWORK_OBJECT_BUFFER_SIZE` (по 1 МБ) — с запасом даже на
`MAX_TOTAL_UNITS` = 300 юнитов, у каждого из которых в худшем случае
длинный путь в обход препятствия.

## Игровые правила

- **Карта.** `GameConstants.MAP_WIDTH/MAP_HEIGHT = 2000`. Сервер клэмпит
  цель движения в эти границы, так что юнита нельзя увести за карту даже
  модифицированным клиентом.
- **Вода.** Прямоугольник `700..1300` по обеим осям посередине карты —
  препятствие для ХОЖДЕНИЯ (не для стрельбы, см. ниже). Юнита нельзя
  отправить точно в воду — такой приказ на движение просто игнорируется.
- **Ресурсы.** Два типа — железо и электричество (`ResourceType`). Хранение
  и рассылка: `PlayerResources` — одновременно авторитетное состояние на
  сервере (`GameServer.resourcesByPlayer`, по объекту на игрока) и то же
  самое поле в `WorldSnapshot.playerResources`, рассылаемое всем одинаково
  (как и юниты — отдельного тумана войны для ресурсов не планируется). На
  клиенте — панель в левом верхнем углу, всегда видна во время игры
  (`GameScreen.drawResourcePanel`), показывает "Iron: N" и
  "Electricity: M" для СВОЕГО игрока (сервер прислал бы оба, но с
  интерфейса на чужие просто не смотрим), а напротив каждого — чистое
  изменение в секунду (`ironRate`/`electricityRate`): зелёным при
  приросте, красным при расходе, белым, если после округления ровно 0.
  Ставка — не отдельно вычисленная "теоретическая" формула из состояния
  зданий (рискованно разошлась бы с `ProductionSystem`/
  `ResourceExtractionSystem` при следующем изменении баланса), а реально
  измеренная сервером разница между двумя последними рассылками снапшота
  (`GameServer.broadcastSnapshot`, хранит `previousResourceValues`) — это
  автоматически учитывает и моменты, когда производство юнита стоит
  из-за нехватки другого ресурса и в этот момент реально ничего не
  тратится, хотя "теоретическая ставка" сказала бы иначе.
- **Здания, которые строит сам игрок: шахта железа, казарма стрелков,
  электростанция, хранилище железа, хранилище электричества.**
  Единственное здание, которое ставит сервер автоматически при входе —
  дом; все остальные пять теперь строит сам игрок. Клавиша **B**
  открывает меню выбора (`GameScreen.showBuildMenu`, пять пунктов);
  после выбора превью следует за курсором до подтверждения ЛКМ или
  отмены повторным B (`placingBuildingType` — `BuildingType`, `null` —
  ничего не строим).

  У шахты принципиально другая логика размещения, чем у казармы и
  станции. **Шахта** может встать только на одно из фиксированных
  месторождений железа — превью "прилипает" к ближайшему в радиусе
  `BuildingDefinitions.snapRadiusFor(IRON_MINE)`, на сервер уходит индекс
  месторождения (`PlaceIronMineRequest{depositIndex}`), не сырые
  координаты — так сервер и клиент гарантированно смотрят на одну и ту
  же точку без риска разойтись по float; `GameServer.handlePlaceIronMine`
  проверяет индекс и что место ещё не занято (`isDepositOccupied` —
  сканирует существующие здания добычи по позиции, без отдельного флага
  "занято", который пришлось бы чистить при разрушении здания).
  **Казарма стрелков и электростанция** нигде на карте не привязаны —
  превью свободно следует за курсором, и клиент, и сервер проверяют одну
  и ту же функцию `BuildingPlacement.canPlaceBuilding(type, ...)` (в
  границах карты, не на воде, не пересекает юнитов или другие здания),
  различие только в том, ЧТО они перебирают (клиент —
  `engine.getEntities()`, сервер — `unitsById.values()`); подтверждение
  шлёт тип здания и координаты напрямую (`PlaceBuildingRequest
  {buildingType, x, y}` — один общий запрос на оба, не два разных),
  окончательное решение — за сервером (`GameServer.handlePlaceBuilding`),
  клиентская проверка лишь не даёт заранее подтвердить явно невалидную
  точку.

  Все три постройки занимают своё `buildTime` из `buildings.json` (10
  сек у всех сейчас, `ConstructionSystem`) и пока ничего не стоят —
  сама ПОСТРОЙКА бесплатна, в отличие от ЭКСПЛУАТАЦИИ казармы и найма
  юнитов (см. ниже). Пока строится — здание видно обеим сторонам
  тускло-серым с прогресс-баром вместо обычного вида, уже нужного
  финального размера. Как только готово — `ConstructionSystem` смотрит
  `BuildingDefinitions` по типу здания (`BuildingComponent.type` —
  единственный источник истины, задаётся один раз при создании) и сама
  добавляет `ResourceExtractorComponent` (шахта, станция) или
  `ProductionComponent` (казарма) — тот же путь, которым идут и дом с
  казармой, если бы у них тоже было время постройки (сейчас 0 —
  появляются сразу готовыми). Различать здания друг от друга (дом —
  золотая звезда, казарма — белая крыша, шахта — ромб цвета
  месторождений, станция — жёлтый кружок, всё в `RenderSystem`) везде
  решает `BuildingComponent.type`, а не отдельные проверки компонентов —
  единая точка расчёта размера здания по этому признаку вынесена в
  `BuildingSizes`, чтобы `CollisionSystem`, `RenderSystem` и клик в
  `GameScreen` не могли разойтись в подсчёте.

  **Известное ограничение:** ни шахта, ни казарма, ни электростанция НЕ
  учтены в статической сетке препятствий `Pathfinding` — она считается
  один раз при загрузке класса по фиксированному месту дома, а эти три
  здания появляются в рантайме по воле игрока, в произвольной (хоть и
  "прилипшей" у шахты) точке. Юниты не будут заранее огибать их по A* на
  большом расстоянии — но `CollisionSystem` всё равно не даст сквозь них
  пройти реактивно (см. её же комментарий про макро/микро-задачи), просто
  не так изящно, как с домом. Осознанный компромисс ради того,
  чтобы не переделывать статическую сетку в динамическую в этой итерации.
- **Экономика: постоянное потребление и стоимость юнитов.** Казарма
  стрелков тратит электричество непрерывно, пока существует —
  `idleConsumptionRate` (0.5/сек в простое) или `activeConsumptionRate`
  (2/сек, пока в очереди есть хотя бы один юнит), решает
  `ProductionSystem` по `production.queuedCount`. Само потребление
  безусловно — не зависит от того, хватает ли ресурсов на юнита (см.
  ниже), и не уходит в минус, а зажимается на 0. Стрелок как юнит
  дополнительно стоит 300 железа и 300 электричества
  (`UnitDefinitions.ironCostFor/electricityCostFor`) — списывается не
  разом, а РАВНОМЕРНО за `UNIT_BUILD_TIME` (сейчас 10 сек → по 30/сек
  каждого ресурса): если на очередной тик не хватает хотя бы одного —
  прогресс постройки просто не растёт, как и при нехватке места под
  юнита (`MAX_TOTAL_UNITS`), ничего не теряется и не уходит в минус.
  Воин по-прежнему бесплатен (`ironCost`/`electricityCost` = 0 в
  `units.json`) — дом ничего не потребляет и не проверяет.

  `PlayerResources.iron`/`electricity` — `float`, не `int`: потребление
  и стоимость считаются дробно (0.5/сек, 30/сек), целочисленное поле
  не смогло бы это накапливать без отдельного аккумулятора. Игроку на
  панели ресурсов число показывается округлённым вниз до целого
  (`GameScreen.drawResourcePanel`) — точность нужна только для
  внутреннего счёта.

  Электростанция при этом производит 150 электричества/сек — сознательно
  куда больше её же прежней ставки (1/сек), потому что 300 электричества
  на одного стрелка иначе набирались бы 5 минут. Скорость добычи железа
  тоже подняли (см. следующий пункт про хранилища) — было такое же узкое
  место при стоимости стрелка в 300 железа.
- **Хранилища — вместимость, а не ещё один источник дохода.** Оба
  ресурса теперь с ограниченной вместимостью (раньше — только железо).
  Базовая вместимость — `GameConstants.baseCapacityFor(ResourceType)`:
  раздельные константы на каждый ресурс (`IRON_BASE_CAPACITY` = 300,
  ровно стоимость одного стрелка; `ELECTRICITY_BASE_CAPACITY` = 2000,
  ~13 сек добычи на полной ставке электростанции), не одна общая — у
  ресурсов слишком разный масштаб потока (150/сек у станции против
  20/сек у шахты), одно число было бы или тесным для электричества, или
  бессмысленно огромным для железа. Здания `IRON_STORAGE`/
  `ELECTRICITY_STORAGE` добавляют к ней свой `storageCapacity` (500 и
  3000 в `buildings.json` соответственно — тоже разного масштаба по той
  же причине) за каждое достроенное (не строящееся) — считает
  `ResourceExtractionSystem.computeCapacities` заново каждый тик для
  ЛЮБОГО здания с непустым `storesResourceType` (общий проход, а не
  раздельный код на каждый ресурс), не полагаясь на закешированное с
  прошлого раза число, которое пришлось бы отдельно чистить при
  разрушении хранилища. Добыча при этом НЕ останавливается, когда
  хранилище полно — здание добычи продолжает "работать" каждый тик,
  просто зачисление зажимается сверху текущей вместимостью
  (`Math.min(resources.iron + amount, capacity)`), а не блокируется
  целиком. Расход ресурса идёт из общего счёта — с точки зрения игрока
  хранилище просто определяет, докуда можно накопить про запас, а не
  откуда именно тратится: отдельного "сначала из хранилища, потом
  дефицит" разделения нет, `resources.iron`/`electricity` — по одному
  числу на ресурс, ниже нуля не уходят, тот же тик-за-тиком гейтинг
  производства (см. выше), что уже был. Ставку добычи шахты заодно
  подняли до 20/сек (было 1) — раньше это было узкое место при
  стоимости стрелка в 300 железа, теперь накопить хватает за 15 сек,
  сравнимо с 10-секундной постройкой самого юнита.
- **Поиск пути.** Если прямая линия от юнита до цели не пересекает
  препятствие — юнит идёт напрямую, как и раньше, без всякого A*. Если
  пересекает (воду ИЛИ здание) — сервер (`Pathfinding`, `shared/pathfinding`)
  считает путь по сетке 40x40 (клетка 50 юнитов) в обход и ведёт юнита по
  нему точка за точкой; клиент об этом не знает вообще ничего — он просто
  видит в снапшотах позицию, которая естественным образом огибает
  препятствие. Это работает и для ручных приказов на движение, и для
  погони в бою (`CombatSystem`) — оба идут через один и тот же
  `Pathfinding.setDestination(...)`. Препятствия раздуты в проверках
  Pathfinding на `PATH_CLEARANCE` (`UNIT_RADIUS + ARRIVE_THRESHOLD`) сверх
  их реального размера (был баг, исправлено): без этого A* мог выбрать
  клетку впритык к краю здания — формально свободную, но ближе
  `UNIT_RADIUS` к стене, так что `CollisionSystem` тут же выталкивала
  юнита обратно, а он тут же шёл туда снова, зависая в вечном топтании у
  стены вместо обхода. Погоня за зданием при атаке идёт не в его точный
  центр (он всегда "внутри" самого здания и потому формально заблокирован
  для Pathfinding), а в точку на `attackRange` от цели по линии к
  атакующему — иначе атаковать здание издалека было бы вообще невозможно.
- **Коллизии.** `CollisionSystem` (сервер, приоритет 20 — после движения)
  каждый тик мягко раздвигает перекрывающиеся юниты, жёстко выталкивает
  юнита, если он всё же оказался внутри здания или воды, и клэмпит
  позицию в границы карты последним шагом — без этого юнита, зажатого у
  края толпой соседей, можно было вытолкнуть прямо за пределы карты
  (был баг, исправлено). Это не противоречит поиску пути, а дополняет
  его: Pathfinding решает макро-задачу (обойти препятствие по дуге
  издалека), CollisionSystem — микро-задачу (не дать юниту в моменте
  влезть в стену или в соседа из-за огрубления сетки или скученности от
  других юнитов). Простая позиционная коррекция постфактум, не физика с
  массой/импульсом — этого достаточно, чтобы юниты не стояли друг в
  друге и не проходили сквозь стены.
- **Групповое движение и "доворот" курса.** `MovementSystem` каждый тик
  заново прицеливается на `direction.target` от текущей позиции, а не
  идёт по один раз посчитанному направлению (тоже был баг, исправлено):
  раньше юнит, которого `CollisionSystem` слегка оттолкнул от соседа при
  скученном групповом приказе, летел по старому курсу мимо цели
  и не останавливался никогда — дистанция до цели просто не сходилась к
  `ARRIVE_THRESHOLD`, если курс не поворачивать вслед за реальной
  позицией. Групповые приказы (`GameScreen.issueMoveOrder`) и так уже
  раскладывают юнитов сеткой на РАЗНЫЕ конечные точки, а не в одну — этого
  в сочетании с "доворотом" курса достаточно для разумного числа юнитов;
  при очень большой скученности локальное расталкивание всё ещё может
  создавать временные заторы (полноценных flow-field/формаций в игре нет)
  — но юниты в итоге доходят, а не ходят вечно.
- **Дом (HQ).** При подключении игрока сервер сразу спавнит ему здание
  (500 HP, `buildings.json`) в одном из противоположных углов карты. Здание — это просто
  сущность без `DirectionComponent`, что и делает её неподвижной для
  `MovementSystem`/`CombatSystem` без единой строчки специального кода.
  Единственное здание, разрушение которого заканчивает игру — см. условие
  победы ниже. Единственное здание, которое сервер ставит сам при входе
  игрока — все остальные (казарма стрелков, шахта железа, электростанция)
  строит сам игрок из меню постройки (клавиша B).
- **Здания разной формы, выровнены по сетке пасфайндера.** Дом — 2×2
  клетки, казарма стрелков — 1×2 (уже дома, той же высоты) — размеры
  заданы в `buildings.json`, не в коде (см. "Баланс зданий" ниже). Дом
  (чётное число клеток по обеим осям — 2×2) должен стоять центром на
  ГРАНИЦЕ клетки, поэтому `spawnMargin` дома — 200 (кратно
  `PATH_GRID_CELL_SIZE`) — единственная формула позиционирования,
  оставшаяся в `BuildingDefinitions`: у остальных трёх зданий позиция
  выбирается самим игроком, заранее её знать неоткуда. Место появления
  произведённого юнита (`BuildingDefinitions.productionSpawnDistanceFor`)
  тоже посчитано по типу здания — для дома и казармы разная диагональ до
  угла их раздутой (на `PATH_CLEARANCE`) зоны, единой константы на
  двоих быть не может.
- **Визуальные метки на зданиях.** Дом и казарма красятся в один и тот
  же цвет игрока — единственное, что отличает их на глаз, это форма и
  значок сверху. На доме — золотая шестиконечная звезда
  (`RenderSystem.drawStar`, два наложенных залитых треугольника —
  простая геометрия вместо настоящей пятиконечной звезды, которую
  `ShapeRenderer` без ручной сборки из треугольников веером не умеет).
  На казарме стрелков — белая "крышечка" (`drawRoofCap`, один залитый
  треугольник поверх верхней грани, силуэтом похожий на двускатную
  крышу). Оба рисуются в том же `ShapeType.Filled`-проходе, что и само
  здание — отдельный `ShapeType.Line`-проход под них заводить не
  пришлось.
- **Производство юнитов.** Юниты создаются только через очередь у своего
  здания — нет ни клика по пустому месту, ни горячей клавиши. ЛКМ по
  своему зданию открывает панель постройки (кнопка "+", прогресс-бар и
  подпись, что здание строит — "Воины" у дома, "Стрелки" у казармы; см.
  `GameScreen.drawProductionPanel`), кнопка ставит в очередь
  (`QueueUnitRequest` -> `GameServer.handleQueueUnit`, просто
  `production.queuedCount++`). Сама постройка — `ProductionSystem`
  (сервер): пока очередь не пуста, копит `progress` и по достижении
  `UNIT_BUILD_TIME` (10 сек) создаёт юнита того типа, который умеет
  строить именно это здание (`ProductionComponent.producesUnitType`) рядом
  со зданием (чуть в сторону центра карты, чтобы не родиться внутри
  самого здания), и снимает его из очереди. Если в этот момент уже
  упёрлись в `MAX_TOTAL_UNITS` — прогресс просто перестаёт расти (не
  пропадает и не переполняется), пока не появится место. Панель — первый
  экранный (не мировой) HUD-элемент в проекте: у неё своя неподвижная
  `hudCamera`, не зависящая от прокрутки основной камеры, и клик по
  кнопке проверяется в её координатах, а не в мировых.
- **Воин и стрелок.** Два типа юнита (`UnitType`, `UnitTypeComponent`).
  Всё, чем один тип отличается от другого в бою — здоровье, скорость,
  скорострельность, урон, дальность атаки — задаётся `units.json` (см.
  следующий пункт), а не Java-константами: чтобы добавить третий тип,
  достаточно дописать запись в файл, не трогая код систем. Сейчас у
  обоих одинаковы здоровье (20), скорость (80), скорострельность
  (4/сек) и урон (2) — разная только дальность атаки (воин — 70,
  стрелок — 210). На клиенте стрелок отличим по маленькой белой точке
  внутри кружка (`RenderSystem`).
- **Баланс юнитов — данные, а не код.** `units.json` (рядом с
  `server.jar`, читается из текущей рабочей директории процесса) задаёт
  на каждый тип юнита `speed`, `health`, `fireRate`, `damage`,
  `attackRadius`, `ironCost` и `electricityCost` (у воина сейчас 0/0 —
  бесплатен; у стрелка 300/300, списывается равномерно за время
  постройки, см. "Экономика" выше). Загружает и раздаёт эти цифры
  `UnitDefinitions` (`shared/UnitDefinitions.java`) — простой
  POJO-загрузчик поверх `com.badlogic.gdx.utils.Json`, без сторонних
  библиотек. Грузится один раз при первом обращении (как статическая
  сетка препятствий в `Pathfinding` — баланс за партию не меняется).
  Если файла нет, он повреждён или не описывает какой-то тип — для
  ЭТОГО типа используются встроенные значения по умолчанию, сервер не
  падает и не отказывается стартовать из-за отсутствующего файла.
  `./gradlew buildJars` копирует `units.json` в `build/dist/` вместе с
  `server.jar`, так что готовую сборку можно донастраивать без
  пересборки Java-кода — просто отредактировать текстовый файл рядом с
  jar-ом. `GameConstants.UNIT_RADIUS` (физический размер для отрисовки и
  коллизий) в JSON намеренно не вынесен — это не боевая характеристика,
  у всех типов он одинаков, и вынос в данные не дал бы ничего, кроме
  лишнего слоя.

  **Радиус атаки — он же радиус авто-агрессии, одна и та же величина,
  не два разных числа.** Раньше был отдельный `AGGRO_RADIUS`, общий на
  всех и заметно меньше дальности атаки; теперь `AggroSystem` для
  каждого юнита берёт его же `attackRadius` из `UnitDefinitions` — у
  кого дальше бьёт, тот дальше и замечает врагов, что интуитивно вернее
  двух независимых чисел. Побочный эффект: у стрелка (210) теперь и
  радиус авто-агрессии 210 — он вступает в бой намного раньше воина
  (70), просто потому что видит дальше.

  **Важно при редактировании `attackRadius`:** он не только "дальность
  стрельбы/агрессии" — тем же числом `CombatSystem` считает точку
  подхода при атаке зданий (см. её комментарий). Если поставить
  `attackRadius` меньше раздутой (на `PATH_CLEARANCE`) половины самого
  крупного здания (сейчас — 62, у дома), юниты этого типа не смогут
  атаковать здания издалека вообще: точка подхода будет попадать внутрь
  заблокированной для `Pathfinding` зоны здания и приказ будет
  проигнорирован.
- **Баланс зданий — тоже данные, а не код.** По вашей просьбе вынесено
  полностью: `buildings.json` (рядом с `server.jar`, та же логика
  поиска файла, что и у `units.json`) задаёт на каждый из шести типов
  здания (`BuildingType`: HOME, ARCHER_BARRACKS, IRON_MINE, POWER_PLANT,
  IRON_STORAGE, ELECTRICITY_STORAGE) `halfWidth`, `halfHeight`,
  `maxHealth`, `buildTime` (0 —
  здание появляется сразу готовым, как сейчас только дом, не через
  `ConstructionComponent`), `producesUnitType` (только у дома/казармы),
  `resourceType`+`extractionRate` (только у шахты/станции),
  `consumesResourceType`+`idleConsumptionRate`+`activeConsumptionRate`
  (только у казармы — см. "Экономика" выше), `spawnMargin` (только у
  дома — отступ от угла карты при автоспавне), `snapRadius` (только у
  шахты), `storesResourceType`+`storageCapacity` (только у обоих
  хранилищ — см. "Хранилища" выше). Загружает `BuildingDefinitions`
  (`shared/BuildingDefinitions.java`) — тот же приём, что
  `UnitDefinitions`: POJO-загрузчик поверх
  `com.badlogic.gdx.utils.Json`, встроенные значения по умолчанию, если
  файла нет/он неполный, `./gradlew buildJars` копирует файл в
  `build/dist/`.

  **Отличие от `units.json` — важное.** Клиенту скорость/урон юнитов не
  нужны, он их не считает сам, поэтому `UnitDefinitions` реально
  вызывал только сервер. А вот размер здания клиенту НУЖЕН — для
  отрисовки правильного прямоугольника и для радиуса клика
  (`RenderSystem`, `GameScreen.clickRadiusFor` — оба через
  `BuildingSizes`). Значит, `buildings.json` должен быть виден
  ОДИНАКОВО обеим сторонам, а не только серверу — если запускать и
  клиент, и сервер из `build/dist/` (как и рекомендуется, см. "Как
  запустить" выше), так и будет; если запускать раздельно через
  `./gradlew :server:run`/`:lwjgl3:run` без общего файла в рабочей
  директории каждого модуля — конфигурации могут разойтись (клиент
  нарисует одно, сервер посчитает по-другому).

  **Единственный источник истины "какое это здание"** — новое поле
  `BuildingComponent.type` (`BuildingType`), задаётся один раз при
  создании и не меняется. Раньше (шахта/станция без Java-константы типа
  здания) это решалось косвенно, по тому, какие ещё компоненты стоят на
  сущности (`ProductionComponent` — значит дом/казарма,
  `ConstructionComponent`/`ResourceExtractorComponent` — значит здание
  добычи); теперь у каждого здания есть прямой ответ на вопрос "какое я
  такое", и вся эта логика (`GameServer.spawnBuilding` — единая функция
  на все четыре типа вместо трёх разных, `BuildingSizes`,
  `ConstructionSystem`, `RenderSystem`) читает именно его, а не гадает.
- **Полёт стрелы.** Когда стреляет именно стрелок (не воин), сервер
  дополнительно рассылает `ProjectileFiredEvent` — чисто косметическое
  сообщение поверх обычного снапшота. Урон применяется на сервере
  мгновенно, хитсканом, в момент выстрела, независимо от этого сообщения
  — оно лишь говорит клиенту нарисовать отрезок, летящий из точки А в
  точку Б за время `дистанция / ARROW_SPEED` (`GameScreen.drawArrows`).
  Сознательное упрощение: секундная нестыковка между "визуально долетела"
  и "урон уже применён" не влияет на исход боя, только на картинку.
- **Бой.** Юниты — 20 HP, скорострельность 4 выстрела/сек, урон 2 за
  выстрел (~2.5 сек на смерть под непрерывным огнём). Здания атакуются
  точно так же, просто с бóльшим запасом HP. Дальность атаки воду не
  учитывает — стрелять через неё можно, вода блокирует только хождение,
  это сознательное упрощение (нет отдельной проверки "линии обзора" для
  боя).
- **Авто-агрессия.** У любого юнита без активного приказа атаковать есть
  радиус авто-агрессии — тот же `attackRadius`, что и у собственно атаки
  (`UnitDefinitions`, `AggroSystem`, сервер; больше не отдельное число —
  см. "Радиус атаки — он же радиус авто-агрессии" выше). Стоит врагу
  оказаться в этом радиусе — юнит сам получает приказ атаковать
  ближайшего из них, тем же путём, что и ручной приказ через ПКМ. Это
  агрессивная стойка безусловно для всех юнитов: приказ на движение
  прерывается, если по пути подвернулся враг, отдельной стойки
  "не атаковать" в игре нет.
- **Условие победы.** Уничтожение дома игрока заканчивает игру: сервер
  замораживает симуляцию и рассылает `GameOverMessage`. Клиент показывает
  "VICTORY"/"DEFEAT"/"DRAW" по центру экрана (текст на английском — см.
  раздел "Управление" выше, откуда и почему это решение).
- **Лимит юнитов** — 300 суммарно на всю игру (не на игрока).
- **Интерполяция движения** — клиент лерпит видимую позицию юнита между
  снапшотами (`InterpolationComponent`/`InterpolationSystem`, чисто
  презентационные, сервер о них не знает).

Подробнее про архитектуру, сознательные упрощения (нет client-side
prediction, нет тумана войны, TCP вместо UDP для снапшотов и т.п.) — в
комментариях исходников `GameServer`, `CombatSystem`, `GameScreen`.

## Gradle

This project uses [Gradle](https://gradle.org/) to manage dependencies.
The Gradle wrapper was included, so you can run Gradle tasks using `gradlew.bat` or `./gradlew` commands.
Useful Gradle tasks and flags:

- `--continue`: when using this flag, errors will not stop the tasks from running.
- `--daemon`: thanks to this flag, Gradle daemon will be used to run chosen tasks.
- `--offline`: when using this flag, cached dependency archives will be used.
- `--refresh-dependencies`: this flag forces validation of all dependencies. Useful for snapshot versions.
- `android:lint`: performs Android project validation.
- `build`: builds sources and archives of every project.
- `buildJars`: builds `server.jar` and `client.jar` and copies both into `build/dist/` — see "Как запустить" above.
- `cleanEclipse`: removes Eclipse project data.
- `cleanIdea`: removes IntelliJ project data.
- `clean`: removes `build` folders, which store compiled classes and built archives.
- `eclipse`: generates Eclipse project data.
- `idea`: generates IntelliJ project data.
- `lwjgl3:jar`: builds the client's runnable jar directly in `lwjgl3/build/libs/client.jar` (prefer `buildJars` from the root — it builds both jars and puts them together).
- `lwjgl3:run`: starts the desktop client.
- `server:jar`: builds the server's runnable jar directly in `server/build/libs/server.jar`.
- `server:run`: starts the headless game server.
- `test`: runs unit tests (if any).

Note that most tasks that are not specific to a single project can be run with `name:` prefix, where the `name` should be replaced with the ID of a specific project.
For example, `core:clean` removes `build` folder only from the `core` project.
