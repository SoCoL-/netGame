# supreme_game

A [libGDX](https://libgdx.com/) project generated with [gdx-liftoff](https://github.com/libgdx/gdx-liftoff),
into which сетевая RTS-логика (создание/движение/бой юнитов, дом игрока,
условие победы) была интегрирована из отдельного прототипа.

## Модули

- `shared` — ECS-компоненты и системы (Ashley), общие для сервера и
  клиента, плюс сетевой протокол (KryoNet-сообщения). Без зависимости на
  графику — только `gdx-core` (математика), `ashley`, `kryonet`.
- `server` — headless-процесс: авторитетная симуляция, применение правил
  игры (лимит юнитов, урон, условие победы). Не использует ни `core`, ни
  графику — только `shared`. Запуск: `./gradlew :server:run`.
- `core`: основной модуль игровой логики, общей для всех клиентских
  платформ — `Main`, `GameScreen`, рендер, ввод, сетевой клиент
  (`ru.socol.supreme.network.GameClient`).
- `lwjgl3`: десктопная платформа (LWJGL3) — было `desktop` в старых доках.
- `android`: мобильная Android-платформа. Нужен Android SDK.

Сервер — это отдельный, самостоятельный процесс, который не собирается ни
в APK, ни в десктопный джар клиента: его запускают на одной машине (обычно
на PC), а клиенты (`lwjgl3` и/или `android`) подключаются к нему по сети.

## Управление

- **WASD / стрелки** — прокрутка камеры (карта 2000x2000, окно не помещает её целиком)
- **ЛКМ клик по своему юниту** — выбрать только его
- **ЛКМ протяжка (рамка)** — выбрать все свои юниты внутри рамки (здания рамкой не выделяются)
- **ЛКМ клик по своему зданию** — открыть/закрыть панель постройки (повторный клик по нему же или клик куда-то ещё закрывает панель)
- **ЛКМ клик по пустому месту** — снять выделение
- **ПКМ по вражескому юниту/зданию** (при непустом выделении) — атаковать им всем выделением сразу
- **ПКМ по пустому месту / своему юниту** — приказ на движение всем выделенным юнитам (несколько юнитов расходятся сеткой вокруг точки клика)
- **`** (клавиша над Tab, слева от "1") — переключает отладочный режим отрисовки (см. ниже)

Весь текст на экране (статус подключения, "VICTORY"/"DEFEAT"/"DRAW", панель
постройки) — на английском, хотя код и README на русском. Причина
техническая: `BitmapFont()` по умолчанию в LibGDX — встроенный битмап-шрифт
только с латиницей, кириллических глифов в нём физически нет, кириллица
рисовалась бы пустыми прямоугольниками. Правильный, но более тяжёлый
вариант — сгенерировать битмап-шрифт из настоящего TTF с кириллицей через
`FreeTypeFontGenerator` (`gdx-freetype` уже есть в зависимостях `core`),
но для этого нужен сам файл шрифта с нужной лицензией, которого в проекте
пока нет. Раз игровой текст минимален, английский — самый простой рабочий
вариант без лишних ассетов.

## Как запустить

**Проще всего — собрать два самодостаточных jar-файла один раз и дальше запускать их напрямую, без Gradle/IDE:**

```bash
./gradlew buildJars
# соберёт build/dist/server.jar и build/dist/client.jar

java -jar build/dist/server.jar
java -jar build/dist/client.jar                 # клиент, сервер на localhost
java -jar build/dist/client.jar 192.168.1.50     # клиент с явным адресом сервера
```

Оба jar-файла самодостаточны (все зависимости внутри, включая нативные
библиотеки LWJGL3 у клиента) — их можно скопировать на другую машину и
запустить одной командой `java -jar ...`, ничего больше не нужно.

Это же решает проблему с кнопкой Run в Android Studio на `main()`: она
использует отдельную синтетическую задачу, которая не подхватывает JVM-флаги
и working directory из `lwjgl3/build.gradle` (в частности
`--enable-native-access=ALL-UNNAMED`, нужный LWJGL3 для создания окна на
новых JDK) — из-за этого окно клиента может не появляться вовсе, при том
что процесс запускается. `java -jar client.jar` (как и `./gradlew :lwjgl3:run`)
этой проблемы не имеет, потому что использует настоящую, полностью
настроенную сборку.

Альтернатива — гонять напрямую через Gradle-таски, без сборки jar-ов
(удобно во время разработки, пересобирает только изменившееся):

```bash
# Сервер (в одном терминале)
./gradlew :server:run

# Десктопный клиент (в другом терминале; для локального теста 2 игроков — ещё в третьем)
./gradlew :lwjgl3:run

# Клиент с явным адресом сервера (по умолчанию — localhost):
./gradlew :lwjgl3:run --args="192.168.1.50"
```

Для Android: соберите/запустите модуль `android` как обычное Android-приложение
(нужен Android SDK и, для эмулятора, `local.properties` с `sdk.dir`). Адрес
сервера сейчас захардкожен в `AndroidLauncher` как `10.0.2.2` — это
специальный алиас Android-эмулятора на loopback хост-машины, где по
умолчанию и предполагается локально запущенный сервер. **На реальном
устройстве это работать не будет** — нужен настоящий IP/хост сервера в
локальной сети или в интернете; для реального использования стоит
добавить экран ввода адреса перед стартом `GameScreen`, вместо константы.

## Слои отрисовки

Два режима, переключаются клавишей `` ` `` (`GameScreen.debugMode`):

- **Обычный** (по умолчанию) — земля залита сплошным цветом:
  `GRASS_COLOR` (зелёный, "трава") на весь `MAP_WIDTH x MAP_HEIGHT`, поверх
  неё `WATER_COLOR` (голубой) точно в границах `GameConstants.WATER_*`.
  Юниты и здания рисуются как раньше, без изменений.
- **Отладочный** — вместо заливки земля разлинована в сетку с шириной
  клетки `PATH_GRID_CELL_SIZE` (та же, с которой работает A*), только
  грани клеток (`ShapeType.Line`), без заливки. Цвет клетки решает
  `Pathfinding.isWaterCell(cx, cy)` — та же классификация (с той же
  `PATH_CLEARANCE`-инфляцией), которую реально видит пасфайндер, а не
  повторение сырой геометрии воды напрямую — это отладочный вид именно
  внутреннего состояния A*, полезный ровно для такого рода багов, какой
  чинили выше. Дополнительно поверх рисуются маршруты всех движущихся
  юнитов оранжевыми линиями — от текущей позиции через
  `direction.target`, дальше через все оставшиеся точки `PathComponent`,
  если юнит обходит препятствие. У юнита без активного движения линии нет.

Маршрут — единственное, что реально гоняется по сети специально ради
отладочного режима: `UnitSnapshot.pathPoints` заполняется сервером всегда
(не только когда у клиента включён debug-режим — специального
клиент-сервер согласования по этому поводу нет, это самый простой вариант
для масштаба проекта, а не потому что дешевле было бы иначе). Здание/цвет
клетки клиент считает сам, без сети — `Pathfinding.isWaterCell` использует
только константы `GameConstants`, одинаковые на клиенте и сервере.

## Игровые правила

- **Карта.** `GameConstants.MAP_WIDTH/MAP_HEIGHT = 2000`. Сервер клэмпит
  цель движения в эти границы, так что юнита нельзя увести за карту даже
  модифицированным клиентом.
- **Вода.** Прямоугольник `700..1300` по обеим осям посередине карты —
  препятствие для ХОЖДЕНИЯ (не для стрельбы, см. ниже). Юнита нельзя
  отправить точно в воду — такой приказ на движение просто игнорируется.
- **Поиск пути.** Если прямая линия от юнита до цели не пересекает
  препятствие — юнит идёт напрямую, как и раньше, без всякого A*. Если
  пересекает (воду ИЛИ здание) — сервер (`Pathfinding`, `shared/pathfinding`)
  считает путь по сетке 40x40 (клетка 50 юнитов) в обход и ведёт юнита по
  нему точка за точкой; клиент об этом не знает вообще ничего — он просто
  видит в снапшотах позицию, которая естественным образом огибает
  препятствие. Это работает и для ручных приказов на движение, и для
  погони в бою (`CombatSystem`) — оба идут через один и тот же
  `Pathfinding.setDestination(...)`. Препятствия раздуты в проверках
  Pathfinding на `PATH_CLEARANCE` (`UNIT_RADIUS + ARRIVE_THRESHOLD`) сверх
  их реального размера (был баг, исправлено): без этого A* мог выбрать
  клетку впритык к краю здания — формально свободную, но ближе
  `UNIT_RADIUS` к стене, так что `CollisionSystem` тут же выталкивала
  юнита обратно, а он тут же шёл туда снова, зависая в вечном топтании у
  стены вместо обхода. Погоня за зданием при атаке идёт не в его точный
  центр (он всегда "внутри" самого здания и потому формально заблокирован
  для Pathfinding), а в точку на `attackRange` от цели по линии к
  атакующему — иначе атаковать здание издалека было бы вообще невозможно.
- **Коллизии.** `CollisionSystem` (сервер, приоритет 20 — после движения)
  каждый тик мягко раздвигает перекрывающиеся юниты, жёстко выталкивает
  юнита, если он всё же оказался внутри здания или воды, и клэмпит
  позицию в границы карты последним шагом — без этого юнита, зажатого у
  края толпой соседей, можно было вытолкнуть прямо за пределы карты
  (был баг, исправлено). Это не противоречит поиску пути, а дополняет
  его: Pathfinding решает макро-задачу (обойти препятствие по дуге
  издалека), CollisionSystem — микро-задачу (не дать юниту в моменте
  влезть в стену или в соседа из-за огрубления сетки или скученности от
  других юнитов). Простая позиционная коррекция постфактум, не физика с
  массой/импульсом — этого достаточно, чтобы юниты не стояли друг в
  друге и не проходили сквозь стены.
- **Групповое движение и "доворот" курса.** `MovementSystem` каждый тик
  заново прицеливается на `direction.target` от текущей позиции, а не
  идёт по один раз посчитанному направлению (тоже был баг, исправлено):
  раньше юнит, которого `CollisionSystem` слегка оттолкнул от соседа при
  скученном групповом приказе, летел по старому курсу мимо цели
  и не останавливался никогда — дистанция до цели просто не сходилась к
  `ARRIVE_THRESHOLD`, если курс не поворачивать вслед за реальной
  позицией. Групповые приказы (`GameScreen.issueMoveOrder`) и так уже
  раскладывают юнитов сеткой на РАЗНЫЕ конечные точки, а не в одну — этого
  в сочетании с "доворотом" курса достаточно для разумного числа юнитов;
  при очень большой скученности локальное расталкивание всё ещё может
  создавать временные заторы (полноценных flow-field/формаций в игре нет)
  — но юниты в итоге доходят, а не ходят вечно.
- **Дом (HQ).** При подключении игрока сервер сразу спавнит ему здание с
  500 HP в одном из противоположных углов карты. Здание — это просто
  сущность без `DirectionComponent`, что и делает её неподвижной для
  `MovementSystem`/`CombatSystem` без единой строчки специального кода.
  Единственное здание, разрушение которого заканчивает игру — см. условие
  победы ниже.
- **Казарма стрелков.** Второе здание, которое сервер спавнит игроку
  вместе с домом — смещено от него в сторону центра карты на
  `ARCHER_BUILDING_OFFSET_DISTANCE` (`GameConstants.archerBuildingSpawnPoint`),
  70 HP (гораздо более хрупкое, чем дом). Разрушение казармы НЕ заканчивает
  игру — она просто не регистрируется в реестре "здание = поражение при
  потере" (`GameServer.buildingIdByPlayer`), в отличие от дома. Лишает
  игрока возможности производить стрелков, если её потерять.
- **Здания выровнены по сетке пасфайндера.** `BUILDING_HALF_SIZE` теперь
  ровно `PATH_GRID_CELL_SIZE / 2` (здание = 1 клетка целиком), а
  `BUILDING_SPAWN_MARGIN` и `ARCHER_BUILDING_OFFSET_DISTANCE` подобраны
  так, чтобы оба здания попадали ровно в ЦЕНТР своей клетки (не на
  границу — раньше дом стоял на 200, что кратно 50, то есть ровно на
  стыке клеток; сейчас на 225 = 4×50+25, это центр клетки), а казарма —
  ровно в 3 диагональных шагах сетки от дома. Раньше эта неровность
  давала два реальных бага: юнит рождался практически на самой границе
  заблокированной зоны собственного здания (`PRODUCTION_SPAWN_DISTANCE`
  была впритык к нужному минимуму), а зазор между домом и казармой на
  случайно выбранном расстоянии (150) получался ~22 юнита — меньше
  половины клетки, так что путь у угла шёл зигзагом (нашли через
  отладочный режим, см. выше). Оба нашлись именно потому, что здания не
  были выровнены по сетке — с выравниванием оба зазора теперь заведомо
  больше клетки и предсказуемы по построению, а не просто "случайно
  хватило места".
- **Производство юнитов.** Юниты создаются только через очередь у своего
  здания — нет ни клика по пустому месту, ни горячей клавиши. ЛКМ по
  своему зданию открывает панель постройки (кнопка "+", прогресс-бар и
  подпись, что здание строит — "Воины" у дома, "Стрелки" у казармы; см.
  `GameScreen.drawProductionPanel`), кнопка ставит в очередь
  (`QueueUnitRequest` -> `GameServer.handleQueueUnit`, просто
  `production.queuedCount++`). Сама постройка — `ProductionSystem`
  (сервер): пока очередь не пуста, копит `progress` и по достижении
  `UNIT_BUILD_TIME` (10 сек) создаёт юнита того типа, который умеет
  строить именно это здание (`ProductionComponent.producesUnitType`) рядом
  со зданием (чуть в сторону центра карты, чтобы не родиться внутри
  самого здания), и снимает его из очереди. Если в этот момент уже
  упёрлись в `MAX_TOTAL_UNITS` — прогресс просто перестаёт расти (не
  пропадает и не переполняется), пока не появится место. Панель — первый
  экранный (не мировой) HUD-элемент в проекте: у неё своя неподвижная
  `hudCamera`, не зависящая от прокрутки основной камеры, и клик по
  кнопке проверяется в её координатах, а не в мировых.
- **Воин и стрелок.** Два типа юнита (`UnitType`, `UnitTypeComponent`).
  Единственное, чем они отличаются в бою — дальность атаки: у стрелка она
  в 3 раза больше, чем у воина (`GameConstants.attackRangeFor`; воин — 70,
  стрелок — 210). Здоровье, скорострельность, урон, скорость движения и
  радиус авто-агрессии одинаковы у обоих типов. На клиенте стрелок
  отличим по маленькой белой точке внутри кружка (`RenderSystem`).
- **Полёт стрелы.** Когда стреляет именно стрелок (не воин), сервер
  дополнительно рассылает `ProjectileFiredEvent` — чисто косметическое
  сообщение поверх обычного снапшота. Урон применяется на сервере
  мгновенно, хитсканом, в момент выстрела, независимо от этого сообщения
  — оно лишь говорит клиенту нарисовать отрезок, летящий из точки А в
  точку Б за время `дистанция / ARROW_SPEED` (`GameScreen.drawArrows`).
  Сознательное упрощение: секундная нестыковка между "визуально долетела"
  и "урон уже применён" не влияет на исход боя, только на картинку.
- **Бой.** Юниты — 20 HP, скорострельность 4 выстрела/сек, урон 2 за
  выстрел (~2.5 сек на смерть под непрерывным огнём). Здания атакуются
  точно так же, просто с бóльшим запасом HP. Дальность атаки воду не
  учитывает — стрелять через неё можно, вода блокирует только хождение,
  это сознательное упрощение (нет отдельной проверки "линии обзора" для
  боя).
- **Авто-агрессия.** У любого юнита без активного приказа атаковать есть
  радиус авто-агрессии — 3 × `UNIT_RADIUS` (`AggroSystem`, сервер). Стоит
  врагу оказаться в этом радиусе — юнит сам получает приказ атаковать
  ближайшего из них, тем же путём, что и ручной приказ через ПКМ. Это
  агрессивная стойка безусловно для всех юнитов: приказ на движение
  прерывается, если по пути подвернулся враг, отдельной стойки
  "не атаковать" в игре нет.
- **Условие победы.** Уничтожение дома игрока заканчивает игру: сервер
  замораживает симуляцию и рассылает `GameOverMessage`. Клиент показывает
  "ПОБЕДА"/"ПОРАЖЕНИЕ"/"НИЧЬЯ" по центру экрана.
- **Лимит юнитов** — 300 суммарно на всю игру (не на игрока).
- **Интерполяция движения** — клиент лерпит видимую позицию юнита между
  снапшотами (`InterpolationComponent`/`InterpolationSystem`, чисто
  презентационные, сервер о них не знает).

Подробнее про архитектуру, сознательные упрощения (нет client-side
prediction, нет тумана войны, TCP вместо UDP для снапшотов и т.п.) — в
комментариях исходников `GameServer`, `CombatSystem`, `GameScreen`.

## Gradle

This project uses [Gradle](https://gradle.org/) to manage dependencies.
The Gradle wrapper was included, so you can run Gradle tasks using `gradlew.bat` or `./gradlew` commands.
Useful Gradle tasks and flags:

- `--continue`: when using this flag, errors will not stop the tasks from running.
- `--daemon`: thanks to this flag, Gradle daemon will be used to run chosen tasks.
- `--offline`: when using this flag, cached dependency archives will be used.
- `--refresh-dependencies`: this flag forces validation of all dependencies. Useful for snapshot versions.
- `android:lint`: performs Android project validation.
- `build`: builds sources and archives of every project.
- `buildJars`: builds `server.jar` and `client.jar` and copies both into `build/dist/` — see "Как запустить" above.
- `cleanEclipse`: removes Eclipse project data.
- `cleanIdea`: removes IntelliJ project data.
- `clean`: removes `build` folders, which store compiled classes and built archives.
- `eclipse`: generates Eclipse project data.
- `idea`: generates IntelliJ project data.
- `lwjgl3:jar`: builds the client's runnable jar directly in `lwjgl3/build/libs/client.jar` (prefer `buildJars` from the root — it builds both jars and puts them together).
- `lwjgl3:run`: starts the desktop client.
- `server:jar`: builds the server's runnable jar directly in `server/build/libs/server.jar`.
- `server:run`: starts the headless game server.
- `test`: runs unit tests (if any).

Note that most tasks that are not specific to a single project can be run with `name:` prefix, where the `name` should be replaced with the ID of a specific project.
For example, `core:clean` removes `build` folder only from the `core` project.
